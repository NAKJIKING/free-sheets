## 1. 사용자 흐름과 화면

```
홈(내 악보함) ─ 하단 FAB ─▶ 액션시트 [새 악보 추가 | 작곡 연습하기 | 악보 라이브러리 | 악보 가져오기 | ★악보 스캔(베타)]
                                                                                     │
  ① 스캔 시작 화면 ──[촬영] image_picker 카메라 / [갤러리] 사진 1장──────────────────┘
        │ (첫 사용이면 ⓪ 모델 받기 시트 — 2절)
  ② 인식 진행 화면 ── 단계 표시 + 인식된 줄부터 목록에 추가
        │
  ③ 결과 화면 ── 줄 목록·미리듣기(내장 신디사이저)·빠르기·조옮김 → [내 악보함에 저장]
        │
  ④ 저장 → 새 곡 생성 → 뷰어로 이동(사진이 악보 페이지, 미리듣기 음원 첨부)
```

| ① 스캔 시작 | 촬영 / 갤러리 두 버튼, 촬영 요령 그림 3컷(정면·한 장 꽉 차게·그림자 없이). 상단 고정 안내: **"한 줄 선율 악보(플루트·바이올린 등)용 — 화음·피아노 악보는 아직 인식하지 못합니다"** | 기존 `pickers.dart` `scanWithCamera`·`pickOnePhoto` 재사용 |

| ④ 저장 | 곡 제목 입력(기본 "스캔 악보 10-06 14:20") → 저장 → 뷰어 | `SongLibrary.createSong`·`addPages` 재사용 |

**진입점 위치**: `home_screen.dart` 하단 FAB 액션시트(:1085-1110)에 한 항목 추가가
유일한 기존 파일 수정이다. 뷰어의 '페이지 추가' 시트(viewer_screen :1708)는
2차 진입점 후보로 남기되 1차에는 넣지 않는다(뷰어는 출시 작업과 겹칠 확률이 큼).

**ML Kit 문서 스캐너(`scanDocumentsWithCamera`)는 1차에서 쓰지 않는다** — 우리
파이프라인(crop_paper·조명 평탄화·되펴기)은 원본 폰 사진으로 검증됐고, ML Kit 의
자체 보정·필터가 들어간 이미지는 정합 검증 밖이다. 나중에 캐논 53장으로 따로
NER 비교 후 채택 여부를 정한다.

**범위 제한(1차, 승인)**: 단선율 파트 악보(플루트·바이올린 등). 성부 분리·화음은 후속.

**단선율 아님 경고(결과 화면 상단 띠)** — omr_core `monophony.dart`. 모델은 화음을
**한 음으로 확신 있게** 읽는다(렌더 실측: 3화음 줄 신뢰도 0.988, 피아노 0.999 —
토큰만으로는 화음을 알 수 없다). 그래서 이미지 신호 두 가지를 쓴다:
① **쌓인 음표머리** — 정규화 줄 텐서에서 오선 행 제거 → 빈 머리 속(작은 구멍)만
채움 → 열기 7 로 기둥·빔·덧줄·임시표 획 제거 → 음표머리 폭(12~22px) 덩어리 중
높이 ≥24px(2칸) 비율 ≥0.08 이면 경고.
② **보표 쌍** — 줄 중심 간격이 작은·큰 두 값으로 교대(교대율 ≥0.8·간격비 ≥1.2).
보정(진행일지 2026-10-07 S1 절): 렌더 양성 전부 경고·함정 0, 실물 단선율 43장 중
겹친 음 오탐 1장·쌍 오탐 0. 한계: 빈 머리(2분·온음표) 화음·2도 화음은 약함 —
실제 화음·피아노 사진으로 S6 재확인. 문구:
- 겹친 음: "한 박자에 여러 음이 겹친 곳이 보여요. 한 줄 선율만 인식하므로 겹친 음은 하나만 들려요."
- 보표 쌍: "두 줄씩 묶인 보표(피아노·2중주)로 보여요. 성부를 나누지 못해 위아래 보표를 차례로 이어서 들려요."
- 둘 다: "화음이나 두 줄 보표(피아노·2중주) 악보로 보여요. 한 줄 선율만 인식하므로 겹친 음은 하나만 들리고, 두 보표는 이어서 들려요."

## 2. 모델 배포 방식 비교

| 항목 | (가) 앱에 내장 | (나) 첫 스캔 때 GitHub 릴리스에서 받기 |
|---|---|---|
| 앱 크기 | AAB 98.9 → 약 **120MB**, 기기별 다운로드 24.5 → 약 **46MB**(+85%). 실수 가중치라 압축 거의 안 됨 | 모델 0MB. 공통 증가분(아래 ORT 네이티브)만 |
| 공통 증가분 | onnxruntime 네이티브 라이브러리 — 기기별(ABI 1종) 약 수~10MB 추정, **시험 빌드로 실측 필요** | 동일 |
| 스캔 안 쓰는 사용자 | 전원이 21MB 부담 | 부담 없음 |
| 오프라인 | 설치 직후 바로 동작 | 첫 스캔 1회만 인터넷 필요, 이후 완전 오프라인 |
| 모델 갱신 | 앱 업데이트(심사)에 묶임 | 매니페스트의 sha256 만 바꿔 새 릴리스 태그 — 단, 매니페스트가 앱에 컴파일돼 있으면 결국 앱 업데이트 필요(현 검수 PDF 방식과 같음) |
| 무결성 | 서명된 APK 안 | sha256 + 바이트 수 검증(검수 PDF 와 같은 수준) |
| 실패 경로 | 없음 | 다운로드 실패·검증 실패·저장공간 부족 안내 필요 |

**기존 `reviewed_pdf_store.dart` 재사용 가능 여부**: 구조(허용 URL 규칙
`github.com/NAKJIKING/free-sheets/releases/download/<tag>/<name>`, 리다이렉트 화이트리스트,
`.part` 임시파일→rename, sha256·길이 검증, 408/429/5xx 3회 재시도, 동시요청 합치기)는
그대로 맞다. 그러나 **PDF 전용 하드코딩**이 있다 — 시작 바이트 `%PDF-` 검사(:140),
`Accept: application/pdf`(:171), `.pdf` 파일명 정규식, 캐시 폴더명. 또 모델에는
맞지 않는 점: ① 캐시 디렉터리(OS·LRU 256MB 가 지울 수 있음 — 모델은
`getApplicationSupportDirectory`가 맞다) ② 전체를 `Uint8List`로 반환(ORT 는 파일
경로로 여는 게 메모리상 유리) ③ 진행률 콜백 없음 ④ 이어받기(Range) 없음
⑤ 전체 제한시간 5분(느린 망 21MB 에 빠듯).

→ **이 파일은 건드리지 않는다**(GPT 출시 검증 대상). 같은 규칙을 따르는
새 파일 `lib/services/omr/model_store.dart`를 만들고, 공통부(URL 검증·리다이렉트·
sha256 스트리밍 검증)는 출시가 끝난 뒤 별도 리팩터로 합친다.

`model_store` 사양: 매니페스트(앱 내장 상수) `{tag, files:[{name:"omr_crnn_fp32.onnx",
bytes, sha256:"6dfc1d66…"}, {name:"vocab.json", bytes, sha256}]}` (정확한 값은
omr_export/export_report.json) → 저장
`appSupport/omr-model-v1/<sha256>.<ext>` → 받는 중 sha256 을 스트리밍으로 계산
(두 번 읽지 않음) → 진행률 콜백(받은 바이트/전체) → `.part` 이어받기(Range) →
제한시간은 무활동 30초 기준(전체 제한 없음) → 검증 통과한 파일만 rename.
릴리스는 free-sheets 에 새 태그 `omr-model-3c4-fp32-01`.

**결정: (나) 내려받기 — 사장님 승인(2026-10-07).** 근거 — 기기별 다운로드가 거의 두 배가 되는 비용을 스캔을
쓰지 않는 다수 사용자에게 지우지 않는다; 이미 같은 방식(검수 PDF)이 운영 중이라
사용자에게 낯설지 않고 검증 규칙도 재사용된다; 1회 21MB 후에는 완전 오프라인.
대안 메모: Play Asset Delivery(on-demand 팩)도 같은 효과지만 빌드 설정(gradle·
bundletool)을 건드려 출시 파이프라인과 충돌 위험이 커서 1차 배제.

**플러그인 확정 절차(S3, 사장님 지시 순서)** — 폰벤치는 pub `onnxruntime 1.4.1` 의
compileSdk 33 고정 문제를 pub 캐시 직접 패치로 넘겼다. **이 방식은 금지**.
1. 패치 없이 빌드되는 onnxruntime 플러그인의 **더 새 버전**이 있는지 확인(pub.dev
   변경 이력·android/build.gradle 의 compileSdk). 있으면 그 버전으로 30줄 벤치 정합
   (폰벤치 시험줄 30/30 일치) 재확인.
2. 없으면 고친 플러그인을 **저장소 안에 포함**(free-sheets `tools/omr_factory/
   third_party/onnxruntime/`, 원본 버전·라이선스·패치 diff·이유를 README 에 기록)하고
   앱은 **path 의존성**으로 연결 — 어떤 컴퓨터·CI 에서도 같은 결과.
   (앱 저장소로 옮기는 시점은 S4 — 앱 저장소 안 경로로 복사, 같은 문서 동봉.)
3. **깨끗한 환경 검증**: 새 PUB_CACHE(빈 임시 폴더)·새 클론에서 `flutter pub get`
   → `flutter build apk --release` 성공 + AAB/APK 크기 증가량 실측 기록.
(벤치 앱 omr_phone_bench 도 같은 방식으로 바꿔 패치 없이 빌드되는지 함께 확인.)

1단계 사전 조회(2026-10-07, pub.dev API): `onnxruntime` 최신은 **1.4.1(2024-03-27)
그대로 — 더 새 버전 없음**. 이름이 다른 후속·대체 패키지는 있다:
`onnxruntime_plus` 1.5.0(2026-07-27, "FFI plugin … cross-platform Dart bindings" —
1.4.1 계열 포크로 보임), `flutter_onnxruntime` 1.9.0(2026-10-06, API 다름). S3 에서
① onnxruntime_plus 가 같은 API 로 패치 없이 빌드되면 그것을 '새 버전'으로 보고
30줄 정합 확인, ② 아니면 2단계(1.4.1 포함·path 의존성)로 간다 — 판단은 사장님께 보고 후.

omr_core 자체는 onnxruntime 에 의존하지 않는다 — 추론은 `LineRecognizer`
인터페이스로 앱이 주입(플러그인 교체가 코어에 영향 없음). 코어의 유일한 외부
의존성은 순수 다트 `image` 패키지(JPEG 디코드·EXIF 회전) — 앱 pubspec 에 새로
추가되는 의존성이므로 S4 에서 버전 충돌 여부 확인.

## 3. 인식 결과 → 앱 형식 변환 경로

```
줄별 CTC id 열 (그리디, blank=0)
  → 어휘 vocab.json: id-1 → [음고, 길이, 붙임줄]  (음고<0 = 기호: −1..−4 반복 구조,
                                                  −5 빠르기 마커, −6..−10 셈여림)
  → 가짜 줄 제거(v5 규칙, 진행일지) → 위→아래 이어붙이기
  → unfold: 반복 전개 (lib_lines.unfold_tokens 이식, 약 40줄)
        pre RS body RE post → pre body body post / 1·2번 괄호 처리
  → 셈여림: −6 f / −8 mf / −7 p → 이후 음의 세기(vel 100/80/60), 크레셴도는 1차 무시
  → 붙임줄 병합 + 기호 토큰 제거 (evaluate.write_midi 병합 로직 이식)
  → 시간화: 4분음표 = 12틱(Q=12), 초 = 틱/12 × 60/bpm, 음고 0 = 쉼표(시간만 전진)
  → List<SynthNote(start초, dur초, key, vel)>
       ├─ 미리듣기: compute(renderWav, SynthRequest(notes:…, samples:…, transpose:…))
       └─ 저장: 같은 노트로 SMF(.mid) 바이트 생성(write_midi 이식, 약 40줄)
```

**기존 앱 코드 재사용**(모두 출시 브랜치 기준 경로):
| 용도 | 재사용 대상 |
|---|---|
| 합성 | `lib/services/midi_synth.dart` `renderWav`·`SynthRequest(notes:)`·`SynthNote` — 노트 목록을 직접 받으므로 미디 파일을 거칠 필요 없음 |
| 피아노 음색 | `piano_samples.dart` `PianoSamples.load()` (샘플 없으면 합성 음색 자동 폴백) |
| 재생 | `wav_playback_io.dart` `wavAudioSource` + just_audio `AudioPlayer`; 흐름은 `free_library_screen.dart` `_togglePreview`(:153-200 — compute 실패 시 메인 스레드 폴백, setSpeed) 그대로 |
| 저장 | `song_library_io.dart` `createSong`(:436), `addPages`(:530, 원본 사진을 악보 페이지로), `setBpm`(:1034), `setTags`(:805, "스캔" 태그) |

**저장 형식(1차, 승인: WAV 첨부 + 미디 동반 보관, 데이터 모델 무변경)**

확인한 제약(출시 브랜치 코드 열람):
- `Song`에는 미디 필드가 없고, 뷰어 오디오 첨부는 `.mid`를 걸러낸다(viewer_screen :3694).
- **전체 백업은 곡 기록이 참조하는 파일만 담는다** — `backup_io.backupFiles`가
  pages·trashedPages·coverPhoto·**audioFileName**·recordings 만 모으고, 복원 때는
  참조 밖 파일을 지운다("Only referenced payload survives"). 곡 복제(duplicateSong)도
  pages·coverPhoto 만 복사한다.
- → 곡 폴더에 따로 둔 `scan.mid`는 **백업·복원에서 사라진다**. 1차 설계안(폴더에
  scan.mid 동봉)은 이 이유로 폐기.

채택안 — **미디를 첨부 WAV 안의 사설 RIFF 청크로 보관**(omr_core `wav_embed.dart`):
- 저장: 합성 WAV(`renderWav`) 끝, 'data' 청크 뒤에 `omrS` 청크를 붙인다. 내용 =
  매직 "OMRS"·판 1·미디(SMF) 바이트·JSON(줄별 토큰·선택 경로·신뢰도·bpm·조옮김·
  모델 sha256·스캔 일시). 이 WAV 를 기존 `setAudio`(파일 복사)로 첨부 →
  `audioFileName`이 가리키므로 **전체 백업·복원에 그대로 포함**.
- 재생: RIFF 규칙상 재생기는 모르는 청크를 건너뛴다(just_audio → 안드로이드
  ExoPlayer WavExtractor·iOS AVFoundation 은 fmt·data 만 읽음). 앱 안의 WAV 직접
  해석은 메트로놈 틱 1곳(viewer_screen :3426, 자체 에셋)뿐이라 영향 없음.
  **S6 실기에서 첨부 재생·구간반복·백업→복원 후 추출을 확인 항목에 넣는다.**
- 꺼내기: `extractScan(wav)` → 미디·토큰 — 빠르기 변경·악보 표시 확장 시 재스캔 불필요.
- 한계(문서화): 사용자가 첨부 음원을 다른 파일로 바꾸거나 지우면 미디도 함께
  사라진다(바꾸기 전 확인 문구는 2차). 곡 공유 패키지·세트리스트 공유는 원래 오디오를
  빼므로 미디도 빠진다(기존 정책과 같음).
- 2차(출시 후 별도 리뷰): `Song.midiFileName` 필드 + backupFiles·공유 패키지 반영.

## 4. 메모리 — 최고 420~500MB 를 램 4GB 폰에서

실측 내역(v4): 모델 세션 + 사진 디코드(회색) + 켬·끔 isolate 2개가 동시에 원해상도
버퍼를 들고 있는 순간이 최고점. 램 4GB 폰은 OS·상주앱 후 가용이 1~1.5GB 라
500MB 는 저메모리 킬러(LMK) 위험권이다. 방안(효과 큰 순):

1. **입력 해상도 상한** — image_picker `maxWidth/maxHeight 3000`(장변). 12MP(4000×3000)
   → 3000×2250 이면 사진 버퍼 44% 감소. 파이프라인은 작업 해상도(WORK_W)로 검출하고
   크롭만 원해상도를 쓰므로 정확도 영향은 캐논 53장으로 사전 검증(게이트 +0.3%p).
2. **기기 등급별 병렬 여부** — `/proc/meminfo` MemTotal(플러그인 없이 다트 파일
   읽기)이 6GB 미만이면 켬·끔 검출을 **순차**로(isolate 1개씩). 대가: A 기준 검출
   4.7 → 약 7초. 6GB 이상은 v4 그대로 병렬.
3. **모델은 파일 경로로 세션 생성** — 폰벤치는 `rootBundle.load` 바이트(다트 힙 21MB
   사본)로 열었다. 내려받기 방식이면 파일 경로 → 다트 힙 사본 없음.
4. **버퍼 즉시 해제** — isolate 결과는 `TransferableTypedData`로 넘겨 복사 0회, 조기
   결정으로 버린 쪽 텐서는 즉시 참조 해제, 인식이 끝나면 세션 `release()`(다음 스캔
   때 재생성 0.3~0.5초 — 메모리 우선).
5. **최고치 감시** — `ProcessInfo.currentRss`를 단계마다 기록(벤치 코드 그대로);
   isolate 오류·OOM 예외를 잡으면 자동으로 "저메모리 모드"(순차 + 장변 2400)로 1회
   재시도 후 실패 안내(5절).

목표: 4GB 등급에서 최고 **350MB 이하**. 검증은 S6 단계에서 램 4GB 실기 1대로
A·B 사진 + 카메라 5장 측정(통과 기준: 강제종료 0회, 최고 RSS ≤ 350MB).

   손대지 않는다.
4. **기능 플래그**(`const kScanEnabled = false` 기본) — 출시 브랜치에 병합돼도
   사용자에게 노출되지 않게. 켜는 결정은 사장님 판정.
5. 버전 번호는 GPT 규칙(Play 마지막 코드 +1, 빌드 인자로 지정)을 따르고 우리가

6. 착수·병합 시점에 AGENTS.md 맨 위에 한 줄 기록(어느 파일을 건드리는지) — 두
   에이전트가 같은 파일을 동시에 고치는 일을 막는다.
