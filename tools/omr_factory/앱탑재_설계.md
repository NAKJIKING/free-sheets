**ML Kit 문서 스캐너(`scanDocumentsWithCamera`)는 1차에서 쓰지 않는다** — 우리
파이프라인(crop_paper·조명 평탄화·되펴기)은 원본 폰 사진으로 검증됐고, ML Kit 의
자체 보정·필터가 들어간 이미지는 정합 검증 밖이다. 나중에 캐논 53장으로 따로
NER 비교 후 채택 여부를 정한다.

**범위 제한(1차, 승인)**: 보표 하나하나가 단선율인 악보 — 독주 파트(플루트·바이올린 등)와
**다성부 합주(2중주·3중주…, 각 보표가 단선율)**. 화음(한 보표 안 여러 음)은 후속.

**다성부 = 파트 나누기(경고 아님, 10-07 사장님 지적 반영)** — omr_core `parts.dart`.
2중주를 위→아래로 이으면 1파트 1줄 → 2파트 1줄 → 1파트 2줄… 로 섞인다. 그래서
같은 단(시스템)의 보표를 묶어 파트를 나눈다. 곡별 상수 없이 **보표 간격**만:
간격을 그 자리 오선 간격 단위로 재고(원근 대응) → 정렬 간격의 가장 큰 비 점프로
작은(단 안)·큰(단 사이)을 나눔(비 ≥1.2·분리도 ≥1.3) → 가장 흔한 단 크기 k(2번 이상)
= 파트 수 → 검출 누락으로 모자란 단은 이웃 단 위치로 파트 자리 추정, 빠진 파트는
그 단 길이 쉼표로 채움(파트 간 박자 정렬). 묶음 괄호·이어진 세로줄 신호는 줄 크롭
밖이라 1차에서는 쓰지 않음(후속 후보).
검증(진행일지 2026-10-07): 캐논 2중주 53장 **전부 2파트**, 파트별 NER 1파트 9.22%·
2파트 7.63%·합 **8.447%**(정답 줄 오라클 배정 8.439% 와 +0.009%p), 단선율 43장
**전부 1파트·미디 바이트 동일(회귀 없음)**. 3·4중주는 렌더로만 확인(정답 일치 0.00%) —
실물 사진 없음, 한 페이지 단 2개 이하·보표 누락이 겹친 3중주는 미검증(한계).
피아노 큰보표는 2파트(오른손·왼손)로 나뉜다.
결과 화면 안내(경고 아님): **"2성부 악보로 인식했어요. 미리듣기에서 파트를 골라 들을 수 있어요."**

**화음 경고(결과 화면 상단 띠)** — omr_core `monophony.dart`. 모델은 화음을
**한 음으로 확신 있게** 읽는다(렌더 실측: 3화음 줄 신뢰도 0.988, 피아노 0.999 —
토큰만으로는 화음을 알 수 없다). 그래서 이미지 신호 **쌓인 음표머리**를 쓴다:
정규화 줄 텐서에서 오선 행 제거 → 빈 머리 속(작은 구멍)만 채움 → 열기 7 로
기둥·빔·덧줄·임시표 획 제거 → 음표머리 폭(12~22px) 덩어리 중 높이 ≥24px(2칸)
비율 ≥0.08 이면 경고. 보정: 렌더 3화음·2중음 전부 경고, 단선율 함정·합주 렌더 0,
실물 96장 오탐 1장(가혹 촬영). 한계: 빈 머리(2분·온음표) 화음·2도 화음은 약함
(피아노 왼손 2분음 화음은 경고 안 뜸) — 실제 화음·피아노 사진으로 S6 재확인. 문구:
- "한 박자에 여러 음이 겹친 곳(화음)이 보여요. 한 줄 선율만 인식하므로 겹친 음은 하나만 들려요."

### 1차 방식: assets 내장

- pubspec `flutter: assets: - assets/omr/` 에 두 파일. 첫 스캔 때 `rootBundle.load` 로 한 번
  꺼내 `getApplicationSupportDirectory()/omr-model-v1/<sha256>.onnx` 에 쓰고 sha256 확인 →
  이후 `OrtSession.fromFile`(플러그인 지원 확인) — 매 스캔마다 21MB 를 다트 힙에 올리지 않는다.
  (복사 순간 한 번 21MB 버퍼가 생김 — 4절 메모리 예산 안.)
- 장점: 설치 직후 오프라인 동작, 다운로드 실패 경로·안내문 불필요, 모델 비공개 유지.
- 단점: **모든 사용자가 다운로드 크기 부담**(아래 실측), 모델 갱신은 앱 업데이트에 묶임.

**앱 크기 증가 실측(2026-10-07)** — 최소 Flutter 앱(기준) vs 같은 앱 + 포함본 플러그인
(onnxruntime_plus 1.5.0) + omr_core + 모델 assets. 둘 다 `flutter build appbundle --release`
→ bundletool 1.18.3 `build-apks` → `get-size total --dimensions=ABI`(Play 기기별 다운로드 크기):

| ABI | 기준 | +스캔 | **증가** |
|---|---|---|---|
| arm64-v8a | 7.16MB | 34.43MB | **+27.3MB** |
| armeabi-v7a | 6.56MB | 33.40MB | **+26.8MB** |
| x86_64 | 7.32MB | 28.04MB | +20.7MB (ORT 라이브러리 없음 — 아래) |

AAB 파일 자체: 43.7MB → 85.4MB(+41.7MB, 두 ABI 라이브러리 + 모델).
증가분 내역(arm64, 압축 추정): 모델 ≈20.3MB(실수 가중치 — deflate 로 7%만 줄어듦) +
ONNX Runtime ≈6.6MB(원본 18.2MB) + 다트 코드(omr_core·image) ≈0.4MB.
→ 내 악보함 현재 기기별 다운로드 24.3~24.9MB(AGENTS.md:374) 기준 **약 51~52MB(×2.1)** 예상.
주의: x86_64 에는 ORT 라이브러리가 없어 그 기기(크롬북·에뮬레이터)에서는 스캔 진입 시
로드 실패 → 앱이 ABI 를 확인해 스캔 메뉴를 숨기거나 안내(S4 항목).

### 향후 선택지: Play Asset Delivery(on-demand 에셋 팩)

모델만 별도 팩으로 빼서 **스캔을 쓰는 사람만** 받게 하는 Google Play 기능. 모델은 Play 를
통해서만 배포되므로 비공개 요건과도 맞다.
- **Flutter 에서 쓰는 법**: Flutter 에는 에셋 팩 전용 공식 API 가 없다. 두 갈래 —
  ① 안드로이드 쪽에 asset-pack 모듈(`omr_model_pack/build.gradle`: `assetPack { packName
  = "omr_model_pack"; dynamicDelivery { deliveryType = "on-demand" } }`)을 만들고 앱
  `build.gradle` 의 `assetPacks = [":omr_model_pack"]` 로 연결, Play Asset Delivery
  라이브러리(`com.google.android.play:asset-delivery`)의 `AssetPackManager` 를
  **플랫폼 채널**(코틀린 수십 줄)로 불러 받기·진행률·위치 조회. ② Flutter 공식
  **deferred components**(Play Feature Delivery — 다트 코드와 에셋을 동적 기능 모듈로
  분리)를 쓰는 방법 — 공식이지만 모델 하나 때문에 다트 코드까지 분리 구조가 생겨 더 무겁다.
  1차 후보는 ①.
- **재사용**: S2 의 `model_store` 중 진행률 표시 흐름·sha256 스트리밍 검증·실패 종류
  (offline·corrupt·storage)는 팩 경로 파일 검증에 그대로 쓸 수 있다(받기 자체는 Play 가 함).
- **시험 방법**: ⓐ 로컬 — bundletool `build-apks --local-testing` + `install-apks` 로
  on-demand 팩 흐름을 기기에서 흉내(Play 없이) ⓑ 실제 — Play Console **내부 테스트 트랙**
  (또는 내부 앱 공유)에 올려 테스터 기기에서 실제 팩 받기 확인. 둘 다 해야 한다(로컬
  모드는 진행률·네트워크 실패를 실제와 다르게 보일 수 있음).
- **복잡도**: 중간 — 그래들 모듈 1개, 플랫폼 채널(코틀린) 1개, 다트 래퍼, 상태 화면
  (받기 전·받는 중·실패) 그리고 **AAB 만으로만 동작**(직접 APK 설치·사이드로드 빌드에서는
  팩이 없음 → 개발·시험 경로가 늘어남), iOS 는 별도(On-Demand Resources). 출시 파이프라인
  (GPT 담당)의 gradle 설정을 건드리므로 그쪽과 일정 협의 필요.
- 전환 시점 제안: 1차 출시 후 스캔 사용률·설치 이탈률을 보고 판단(크기 ×2.1 이 설치에
  영향을 주는지).

### S2 내려받기 모듈 — **보관, 1차 앱 흐름에서는 쓰지 않음**

`omr_core/lib/src/model_store.dart`(+시험 10건)는 지우지 않고 보관한다. 1차 앱은 이
모듈을 호출하지 않는다. 매니페스트 상수 `omrModel3c4` 의 태그 이름은 **게시 금지**

## 3. 인식 결과 → 앱 형식 변환 경로

```
줄별 CTC id 열 (그리디, blank=0)
  → 어휘 vocab.json: id-1 → [음고, 길이, 붙임줄]  (음고<0 = 기호: −1..−4 반복 구조,
                                                  −5 빠르기 마커, −6..−10 셈여림)
  → 가짜 줄 제거(v5 규칙, 진행일지)
  → 파트 나누기(parts.dart): 단선율이면 위→아래 이어붙인 1파트, 다성부면 단마다
     보표를 파트에 배정해 파트별로 이어붙임(빠진 자리는 단 길이 쉼표)
  → (파트마다) unfold: 반복 전개 (lib_lines.unfold_tokens 이식, 약 40줄)
        pre RS body RE post → pre body body post / 1·2번 괄호 처리
  → 셈여림: −6 f / −8 mf / −7 p → 이후 음의 세기(vel 100/80/60), 크레셴도는 1차 무시
  → 붙임줄 병합 + 기호 토큰 제거 (evaluate.write_midi 병합 로직 이식)
  → 시간화: 4분음표 = 12틱(Q=12), 초 = 틱/12 × 60/bpm, 음고 0 = 쉼표(시간만 전진)
  → List<SynthNote(start초, dur초, key, vel)>
       ├─ 미리듣기: compute(renderWav, SynthRequest(notes:…, samples:…, transpose:…))
       │    다성부: 고른 파트의 노트만, '함께'면 모든 파트 노트를 합쳐(시작 시각 기준) 합성
       └─ 저장: SMF 바이트(writeMidiParts) — 1파트면 형식 0(기존과 같은 바이트),
            다성부면 형식 1·파트마다 트랙·채널 j(빠르기는 첫 트랙)
```

**기존 앱 코드 재사용**(모두 출시 브랜치 기준 경로):
| 용도 | 재사용 대상 |
|---|---|
| 합성 | `lib/services/midi_synth.dart` `renderWav`·`SynthRequest(notes:)`·`SynthNote` — 노트 목록을 직접 받으므로 미디 파일을 거칠 필요 없음 |
| 피아노 음색 | `piano_samples.dart` `PianoSamples.load()` (샘플 없으면 합성 음색 자동 폴백) |
| 재생 | `wav_playback_io.dart` `wavAudioSource` + just_audio `AudioPlayer`; 흐름은 `free_library_screen.dart` `_togglePreview`(:153-200 — compute 실패 시 메인 스레드 폴백, setSpeed) 그대로 |
| 저장 | `song_library_io.dart` `createSong`(:436), `addPages`(:530, 원본 사진을 악보 페이지로), `setBpm`(:1034), `setTags`(:805, "스캔" 태그) |

**저장 형식(1차, 승인: WAV 첨부 + 미디 동반 보관, 데이터 모델 무변경)**

확인한 제약(출시 브랜치 코드 열람):
- `Song`에는 미디 필드가 없고, 뷰어 오디오 첨부는 `.mid`를 걸러낸다(viewer_screen :3694).
- **전체 백업은 곡 기록이 참조하는 파일만 담는다** — `backup_io.backupFiles`가
  pages·trashedPages·coverPhoto·**audioFileName**·recordings 만 모으고, 복원 때는
  참조 밖 파일을 지운다("Only referenced payload survives"). 곡 복제(duplicateSong)도
  pages·coverPhoto 만 복사한다.
- → 곡 폴더에 따로 둔 `scan.mid`는 **백업·복원에서 사라진다**. 1차 설계안(폴더에
  scan.mid 동봉)은 이 이유로 폐기.

채택안 — **미디를 첨부 WAV 안의 사설 RIFF 청크로 보관**(omr_core `wav_embed.dart`):
- 저장: 합성 WAV(`renderWav`) 끝, 'data' 청크 뒤에 `omrS` 청크를 붙인다. 내용 =
  매직 "OMRS"·판 1·미디(SMF) 바이트·JSON(줄별 토큰·선택 경로·신뢰도·bpm·조옮김·
  모델 sha256·스캔 일시). 이 WAV 를 기존 `setAudio`(파일 복사)로 첨부 →
  `audioFileName`이 가리키므로 **전체 백업·복원에 그대로 포함**.
- 재생: RIFF 규칙상 재생기는 모르는 청크를 건너뛴다(just_audio → 안드로이드
  ExoPlayer WavExtractor·iOS AVFoundation 은 fmt·data 만 읽음). 앱 안의 WAV 직접
  해석은 메트로놈 틱 1곳(viewer_screen :3426, 자체 에셋)뿐이라 영향 없음.
  **S6 실기에서 첨부 재생·구간반복·백업→복원 후 추출을 확인 항목에 넣는다.**
- 다성부: 청크의 미디는 **항상 전체(파트별 트랙)**, JSON 에 파트 수·단/파트 배정·
  WAV 에 담긴 선택('함께' 또는 n파트)을 기록. 첨부 WAV 의 소리는 ③에서 고른 것.
  나중에 다른 파트로 바꿔 들으려면 청크의 미디에서 다시 합성(재스캔 불필요).
- 꺼내기: `extractScan(wav)` → 미디·토큰 — 빠르기 변경·악보 표시 확장 시 재스캔 불필요.
- 한계(문서화): 사용자가 첨부 음원을 다른 파일로 바꾸거나 지우면 미디도 함께
  사라진다(바꾸기 전 확인 문구는 2차). 곡 공유 패키지·세트리스트 공유는 원래 오디오를
  빼므로 미디도 빠진다(기존 정책과 같음).
- 2차(출시 후 별도 리뷰): `Song.midiFileName` 필드 + backupFiles·공유 패키지 반영.

## 4. 메모리 — 최고 420~500MB 를 램 4GB 폰에서

실측 내역(v4): 모델 세션 + 사진 디코드(회색) + 켬·끔 isolate 2개가 동시에 원해상도
버퍼를 들고 있는 순간이 최고점. 램 4GB 폰은 OS·상주앱 후 가용이 1~1.5GB 라
500MB 는 저메모리 킬러(LMK) 위험권이다. 방안(효과 큰 순):

1. **입력 해상도 상한** — image_picker `maxWidth/maxHeight 3000`(장변). 12MP(4000×3000)
   → 3000×2250 이면 사진 버퍼 44% 감소. 파이프라인은 작업 해상도(WORK_W)로 검출하고
   크롭만 원해상도를 쓰므로 정확도 영향은 캐논 53장으로 사전 검증(게이트 +0.3%p).
2. **기기 등급별 병렬 여부** — `/proc/meminfo` MemTotal(플러그인 없이 다트 파일
   읽기)이 6GB 미만이면 켬·끔 검출을 **순차**로(isolate 1개씩). 대가: A 기준 검출
   4.7 → 약 7초. 6GB 이상은 v4 그대로 병렬.
3. **모델은 파일 경로로 세션 생성** — 폰벤치는 `rootBundle.load` 바이트(다트 힙 21MB
   사본)로 열었다. 1차(내장)는 첫 스캔 때 한 번만 앱 저장소로 복사한 뒤
   `OrtSession.fromFile` → 이후 다트 힙 사본 없음.
4. **버퍼 즉시 해제** — isolate 결과는 `TransferableTypedData`로 넘겨 복사 0회, 조기
   결정으로 버린 쪽 텐서는 즉시 참조 해제, 인식이 끝나면 세션 `release()`(다음 스캔
   때 재생성 0.3~0.5초 — 메모리 우선).
5. **최고치 감시** — `ProcessInfo.currentRss`를 단계마다 기록(벤치 코드 그대로);
   isolate 오류·OOM 예외를 잡으면 자동으로 "저메모리 모드"(순차 + 장변 2400)로 1회
   재시도 후 실패 안내(5절).

목표: 4GB 등급에서 최고 **350MB 이하**. 검증은 S6 단계에서 램 4GB 실기 1대로
A·B 사진 + 카메라 5장 측정(통과 기준: 강제종료 0회, 최고 RSS ≤ 350MB).
